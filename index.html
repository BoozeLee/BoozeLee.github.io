The part that matters

Most AI tooling demos show you the happy path. I build the part that decides whether the thing is actually right — and I make the check itself trustworthy, because a green test that cannot fail is worse than no test.

Concretely: I write gates that must fail when seeded with a mutated claim, bind every published number to a checksum so it cannot drift silently, and keep the failure list honest instead of rounding it away.

MIT · BoozeLee/elohim

elohim — a checksum gate for numerical claims

An agent-skill ledger that pins each published number to a checksum and refuses any value it cannot re-derive. It is also instrumented against itself: seeded mutations must be caught.

81 facts classified 107 checksum-pinned values 38/38 traps re-derived 6/6 tampered copies caught 7 shipped skills 20,639 non-blank tracked lines 
git clone https://github.com/BoozeLee/elohim && cd elohim
python3 tests/test_all.py        # -> ALL_SKILLS_PASS

The tamper suite seeds six broken copies and asserts each one produces verdict FAIL with a PIN DRIFT report. A gate that cannot be made to fail is not evidence, so failing is the tested behaviour.

Figures are pinned to commit 114f660 and are re-derivable there forever. The repository is being actively developed, so figures on its current main may already be higher.

AGPL-3.0-only · galacticfederation / repotruth

repotruth — catch AI-written claims before they ship

Repositories drift. AI tooling writes confident summaries of code that stopped existing months ago. repotruth diffs the claims against the repo and fails the build when a description no longer matches the code.

How I work

  • Measure before claiming. A number I cannot re-derive does not go on a page.
  • Negative controls. Before trusting a gate, I break it on purpose and confirm it notices.
  • Honest failure lists. A harness that reports 17/20 with reasons is more useful than one claiming 20/20.
  • Delete, don't soften. An unsupported claim gets cut and logged. Vague wording is still a false claim.
